# ADR 0002: x11rb como biblioteca X11 y garantías de `unsafe`

- **Estado:** aceptado. Verificado el 2026-10-11 (P3) sobre x11rb 0.14.0 y
  x11rb-protocol 0.14.0, fijados en `Cargo.lock`.
- **Fecha:** 2026-10-11 (referencias de línea a x11rb revisadas el
  2026-10-12)

## Contexto

El WM necesita hablar el protocolo X11, incluidas más adelante las
extensiones RandR y XKB, sin bloques `unsafe` injustificados en el código
propio.

## Decisión

Las rutas de esta sección son relativas a
`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`.

1. **x11rb** con `RustConnection`: una implementación del protocolo en
   Rust que no enlaza libxcb.
2. **`default-features = false`.** F1 solo usa el protocolo base. Las
   extensiones (`randr`, `xkb`…) se activarán cuando una fase las necesite.
   - x11rb 0.14.0 **no declara ninguna feature `default`**
     (`x11rb-0.14.0/Cargo.toml`), así que `default-features = false` no
     cambia la selección: deja la intención explícita y protege frente a
     una futura feature por defecto.
   - `RustConnection` está disponible sin features: el módulo
     `rust_connection` no depende de ninguna (`x11rb-0.14.0/src/lib.rs:174`)
     y el crate compila con esta configuración.
   - x11rb-protocol sí tiene `default = ["std"]`, y x11rb la activa. Es la
     única feature activa de ese crate.
3. **No se activa la feature `allow-unsafe-code`.** En x11rb 0.14.0:
   - Activa las dependencias opcionales `libc` y `as-raw-xcb-connection`
     (`x11rb-0.14.0/Cargo.toml`).
   - Habilita el módulo `xcb_ffi`, que contiene `XCBConnection` (libxcb por
     FFI) (`src/lib.rs:161-162`), y el tipo `CSlice`
     (`src/utils.rs:13-99`). La documentación lo describe así: «Without
     this flag, `xcb_ffi::XCBConnection` and some support code for it are
     unavailable» (`src/lib.rs:101-102`).
4. **El código propio prohíbe `unsafe`** (`unsafe_code = "forbid"` en el
   `Cargo.toml`).
5. **Conexión.** El proyecto no usa `RustConnection::connect`, por las
   razones de la sección "Conexión al servidor"; la conexión se construye
   con las funciones públicas descritas allí (decisión en el ADR 0003).

## Garantías: código propio frente a dependencias

Las garantías de nuestro código **no se extienden** a las dependencias. El
recuento de `unsafe` es preliminar, hecho con `grep`, y **no es una
auditoría de seguridad** (detalle en `docs/dependencies.md`, §4).

| Ámbito | Situación | Fuente (2026-10-11) |
|---|---|---|
| Código de Crimson WM | `unsafe` prohibido por lint. | `Cargo.toml` |
| x11rb 0.14.0 | `#![cfg_attr(not(feature = "allow-unsafe-code"), forbid(unsafe_code))]`. Sin la feature, el código que se compila no contiene `unsafe`; todos los usos están en módulos condicionados a ella. | `src/lib.rs:147`, `src/lib.rs:161-162`, `src/utils.rs:13-99` |
| x11rb-protocol 0.14.0 | `unsafe_code` en `#![forbid(...)]`, y `#![no_std]`. | `src/lib.rs:55-69` |
| rustix 1.1.5 | Usa `unsafe` para las llamadas al sistema; `#![cfg_attr(linux_raw, deny(unsafe_code))]` en la raíz. Sin revisar. | `src/lib.rs:101`; recuento con `grep` |
| linux-raw-sys 0.12.1 | Bindings generados del kernel, sin lint en la raíz. Sin revisar. | Recuento con `grep` |
| gethostname 1.1.0 | Dos bloques `unsafe`, ambos en código `#[cfg(windows)]`; no se compilan en Linux. | `src/lib.rs:60-100` |
| bitflags 2.13.2 | `#![cfg_attr(not(test), forbid(unsafe_code))]`. Sus dos `unsafe impl` están en la integración con `bytemuck`, que no está activa. | `src/lib.rs:273`, `src/external.rs:236-243` |

No se afirma que el árbol de dependencias esté libre de `unsafe`: rustix y
linux-raw-sys lo contienen y no se ha revisado.

## Conexión al servidor (x11rb 0.14.0)

- **Parser público de `DISPLAY`:**
  `x11rb_protocol::parse_display::parse_display(dpy_name: Option<&str>)
  -> Result<ParsedDisplay, DisplayParsingError>`
  (`x11rb-protocol-0.14.0/src/parse_display/mod.rs:43`), disponible con la
  feature `std`. Desde Crimson WM es accesible mediante
  `x11rb::reexports::x11rb_protocol` (`x11rb-0.14.0/src/lib.rs:153-155`),
  sin declarar x11rb-protocol como dependencia directa.
  - Devuelve `ParsedDisplay { host, protocol, display: u16, screen: u16 }`.
  - Errores: `DisplayNotSet`, `MalformedValue`, `NotUnicode` y `Unknown`.
  - Los valores que empiezan por `/` o por `unix:` se tratan como una ruta
    de socket: si el archivo existe (o existe tras quitar un sufijo `.n` de
    pantalla) se devuelven con `protocol = "unix"`, `host = <ruta>` y
    **siempre `display = 0`**; si no existe, como `MalformedValue`
    (`mod.rs:72-77` y `113-142`). La existencia se comprueba con
    `Path::exists` (`mod.rs:44-46`), así que una ruta relativa depende del
    directorio de trabajo. Por eso `unix:5` se interpreta como la ruta
    relativa `5`, no como el display 5.
  - Los números se analizan con `u16::from_str`, que acepta ceros a la
    izquierda y el signo `+` (`mod.rs:96-100`).
- **`RustConnection::connect`**
  (`x11rb-0.14.0/src/rust_connection/mod.rs:112-158`): vuelve a leer
  `DISPLAY` si recibe `None`; para `:N` prueba el socket
  `/tmp/.X11-unix/X<N>` y, si falla, **TCP en `localhost:6000+N`**
  (`x11rb-protocol-0.14.0/src/parse_display/connect_instruction.rs:38-48`);
  e **ignora los errores de autenticación** y conecta sin ella
  (`mod.rs:130-134`).
- **Funciones públicas para una conexión explícita:**
  - `DefaultStream::connect(&ConnectAddress)
    -> Result<(DefaultStream, (Family, Vec<u8>))>`
    (`x11rb-0.14.0/src/rust_connection/stream.rs:161`). Con
    `ConnectAddress::Socket(ruta)` usa `UnixStream::connect` y devuelve la
    familia `LOCAL` con el nombre del equipo (`stream.rs:519-524`).
  - `x11rb_protocol::xauth::get_auth(family, address, display)
    -> Result<Option<(Vec<u8>, Vec<u8>)>, std::io::Error>`
    (`x11rb-protocol-0.14.0/src/xauth.rs:248`). Lee el archivo de
    `XAUTHORITY` o, si no está definida, `$HOME/.Xauthority`
    (`xauth.rs:131-141`), y solo devuelve entradas `MIT-MAGIC-COOKIE-1`.
    Devuelve `Ok(None)` si no puede determinar la ruta (ni `XAUTHORITY` ni
    `HOME` definidas) o si ninguna entrada coincide; si el archivo no
    existe o no se puede abrir, devuelve ese error (`xauth.rs:150-161`).
  - `RustConnection::connect_to_stream_with_auth_info(stream, screen,
    auth_name, auth_data)`
    (`mod.rs:180`). Tras recibir la respuesta de conexión, comprueba en el
    cliente que el número de pantalla es menor que el de pantallas que
    anuncia el servidor; si no, devuelve `InvalidScreen` (`mod.rs:245-248`).

## Alternativas consideradas

- **Crate `xcb`:** enlaza libxcb por FFI y requiere `unsafe`.
- **Crate `x11` (Xlib):** FFI de bajo nivel con `unsafe` extendido.
- **penrose, leftwm:** solo como referencia de lectura, respetando sus
  licencias; no como dependencias.

## Consecuencias

- Licencias de las versiones fijadas (`cargo metadata`, 2026-10-11):
  - x11rb 0.14.0, x11rb-protocol 0.14.0 y bitflags 2.13.2:
    `MIT OR Apache-2.0`.
  - rustix 1.1.5 y linux-raw-sys 0.12.1:
    `Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`.
  - gethostname 1.1.0: **solo `Apache-2.0`**.
  - Las dependencias que solo se usan en otras plataformas figuran en
    `docs/dependencies.md`, §3.2.

  La compatibilidad de `Apache-2.0` con la licencia del proyecto se evaluará
  cuando el autor la elija.
- Activar `allow-unsafe-code`, añadir una extensión, cambiar de biblioteca o
  actualizar x11rb requiere actualizar este ADR y `docs/dependencies.md`, y
  volver a verificar las referencias a las fuentes.
